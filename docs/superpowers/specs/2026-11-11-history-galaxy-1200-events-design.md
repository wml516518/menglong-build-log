# 历史星河 1200 条真实事件内容扩充设计

## 目标

将《历史星河》的生产内容从 30 条代表事件扩充为 1200 条可追溯的中国历史事件，覆盖先秦至 1949 年。所有事件必须能够在正式站中搜索、筛选、点击并打开档案；约 200 条核心事件提供完整叙事，其余 1000 条提供可靠的基础档案。

本阶段只扩充内容及其必要的数据管线，不重新设计 3D 场景、聚类视觉、粒子效果或布局密度。远景仍按现有语义层级和屏幕空间聚类展示，1200 条事件不会在最外层同时显示为带标题的独立光点。

## 非目标

- 不用性能测试中的模拟事件替代真实历史内容。
- 不为凑够数量发布缺少来源、年代不可判断或与既有条目高度重复的记录。
- 不在本阶段重做 3D 交互、专题路线播放或人物关系可视化。
- 不要求 1200 条事件全部达到长篇百科文章的深度。
- 不把生成目录作为编辑源；`public/history-content/generated` 仍由编译器完整重建。

## 内容范围与配额

事件使用九个互斥的编辑归类统计配额。并立政权使部分归类的年代范围客观重叠，但同一事件只能计入一个归类。视觉导航可以继续将归类映射为现有的唐、五代、宋、元、明、清和近代入口。

| 编辑时期 | 年代范围 | 事件数 | 核心事件数 |
| --- | ---: | ---: | ---: |
| 先秦 | 约公元前 2070 年至公元前 221 年 | 170 | 25 |
| 秦汉 | 公元前 221 年至 220 年 | 130 | 22 |
| 魏晋南北朝 | 220 年至 589 年 | 120 | 18 |
| 隋唐五代 | 581 年至 960 年 | 160 | 30 |
| 宋辽金夏 | 907 年至 1279 年 | 170 | 30 |
| 元 | 1271 年至 1368 年 | 70 | 12 |
| 明 | 1368 年至 1644 年 | 130 | 22 |
| 清前中期 | 1644 年至 1840 年 | 130 | 21 |
| 近代史 | 1840 年至 1949 年 | 120 | 20 |

时期边界存在政权并立和过渡重叠。每个事件只归入一个 `editorialPeriodId` 以保证配额互斥；相关政权通过 `polityIds` 表达，视觉入口通过独立的导航映射决定，不使用重复事件满足多个时期配额。

## 内容深度

### 基础事件

1000 条 `detailLevel: "basic"` 的基础档案必须包含：

- 唯一 ID、规范标题和必要别名
- 起止年代及 `exact`、`circa`、`decade`、`century` 或 `range` 精度
- 编辑时期、视觉时代、相关政权
- 至少一个历史分类
- 80 至 150 字中文摘要
- 影响力 1 至 5
- 已登记的人物、地点、父子事件和关系引用；没有可靠资料时允许相应数组为空
- 至少一个带具体定位的来源引用
- 稳定、确定性的布局元数据

基础事件点击后展示年代、摘要、分类、来源和已登记关联。界面不得伪造不存在的起因、过程或人物关系。

### 核心事件

200 条核心事件在基础字段之外还必须包含：

- 历史背景
- 一项以上起因
- 至少一个过程节点
- 一项以上结果
- 一项以上分维度影响
- 史学说明或争议说明
- 主要人物和相关事件
- 至少两个不同来源

现有 30 条事件全部作为核心事件迁移，不得因目录重构丢失已有正文和人物关联。

## 源文件架构

编辑源位于 `history-content`：

```text
history-content/
  catalog/
    events/
      pre-qin.json
      qin-han.json
      wei-jin.json
      sui-tang-five-dynasties.json
      song-liao-jin-xia.json
      yuan.json
      ming.json
      qing.json
      modern.json
  content/
    <visual-era>/events/<event-id>.md
    <visual-era>/people/<person-id>.md
  manifest/
    eras.json
    editorial-periods.json
    sources.json
    places.json
    polities.json
    themes.json
    relations.json
```

九个事件目录合计保存 1200 条基础元数据。核心 Markdown 只保存事件 ID 和增强字段，编译时与目录记录合并；基础元数据不在 JSON 和 Markdown 中重复维护。人物、地点、政权和来源使用注册表 ID 引用。

现有 Markdown 的完整 frontmatter 在迁移时拆分：公共元数据进入事件目录，背景正文和叙事字段留在 Markdown。迁移完成后，编译器拒绝核心 Markdown 再次声明目录拥有的字段。

## Schema

新增并导出以下概念：

- `EditorialPeriod`：互斥的九时期配额单元。
- `SourceReference`：`sourceId`、具体卷章/页码/条目或网页段落定位 `locator`，以及可选说明 `note`。
- `BasicEventRecord`：全部 1200 条线上事件共有的基础字段，包含 `detailLevel: "basic" | "core"`。
- `CoreEventDetails`：只在核心 Markdown 中出现的背景、起因、过程、结果、影响和史学说明。
- `HistoryEventArchive`：编译后的基础记录与可选核心详情联合类型。

编辑源使用 `sourceRefs: SourceReference[]`。生成的紧凑索引只派生保留 `sourceIds` 和 `detailLevel`，使列表与搜索结果能够区分基础档案和核心档案，同时不携带较长的来源定位文本。时代分包包含完整 `sourceRefs`、该时代的基础事件以及核心事件详情；不再假定每条事件都有长篇字段。

## 来源政策

来源优先级如下：

1. 权威通史、断代史、历史大辞典和百科全书。
2. 国家博物馆、故宫博物院、国家档案馆及高校历史院系公开资料。
3. 可核对版本的正史、编年史、文集和出土文献整理本。
4. 具备作者、机构和稳定链接的专题论文或公开文章。

每个来源在 `sources.json` 中只登记一次。事件通过 `SourceReference` 记录具体定位，不接受只有书名而没有卷、章、页码、条目或网页定位的引用。网页来源必须使用 HTTPS 并保存访问日期。

年代或解释存在争议时使用相应精度，并在核心事件的史学说明或基础事件的来源说明中列出分歧。不得把推断性日期存为 `exact`，不得为缺乏资料的事件虚构人物、地点或因果关系。

## 分类覆盖

事件覆盖政治、战争、制度、经济、科技、文化、思想、宗教、外交、民族关系和社会生活。编译报告输出各时期、各分类和各影响力等级的数量。

以下情况视为质量失败：

- 任一分类在全部 1200 条事件中为零。
- 政治与战争合计超过全部事件的 60%，导致内容明显偏科。
- 某时期只有政治、战争两类内容。
- 影响力 5 的事件超过总数的 15%，导致重要性等级失去区分度。

这些约束只控制明显失衡，不要求每个历史时期机械地平均分配所有分类。

## 编译流程

`scripts/history-content.ts` 扩展为以下确定性流程：

1. 读取时期、时代、来源、人物、地点、政权、专题和关系注册表。
2. 读取九个事件目录并验证单条基础记录。
3. 读取核心事件 Markdown，按 ID 合并核心详情。
4. 验证总数、时期配额、核心数量、来源数量和分类覆盖。
5. 验证年代范围、跨记录引用、父子关系、关系端点及人物双向关联。
6. 检测重复 ID、规范化标题重复、别名冲突和高度疑似重复记录。
7. 生成紧凑索引、时代分包、来源目录、关系目录和兼容索引。
8. 使用现有原子目录替换机制发布生成结果。

`history:check` 只读验证编辑源；`history:compile` 在全部验证通过后重建生成目录。编译报告必须输出事件总数、基础/核心数量、九时期配额、分类分布、人物数、地点数、来源数和错误数。

## 重复检测

确定性重复检测包括：

- 相同 ID 或规范化标题直接失败。
- 同一时期内，年代范围高度重叠且标题或别名高度相似的记录标记为疑似重复。
- 父事件与子事件允许年代重叠，但必须建立显式父子关系。
- 同一历史过程可拆为多个事件，前提是标题、时间范围和摘要说明各自边界，并使用关系或父子关系连接。

疑似重复列表作为编译错误输出，必须通过合并条目、调整边界或显式父子关系消解，不设置忽略全部的全局开关。

## 前端数据流

首次进入历史星河时加载包含 1200 条记录的紧凑事件索引，用于星点、列表、搜索、筛选和聚类。进入事件侧栏或完整档案时，按事件的视觉时代加载一个时代分包。

基础事件档案只渲染真实存在的字段，并明确显示为“基础档案”；核心事件渲染完整的背景、起因、过程、结果、影响和人物网络。来源区在两种档案中都可见。

当前 LOD、聚类、搜索 Worker、筛选状态、相机恢复和 2D 降级保持不变。重大事件、当前选中事件和搜索命中事件继续受到可见性保护。最外层全景继续显示关键事件与聚类；“线上包含 1200 条”通过事件列表总数、搜索结果和时代计数明确体现，而不是强制一次显示 1200 个标签。

## 内容生产流程

内容按九时期分别建立候选清单，再执行以下步骤：

1. 从权威年表、通史目录和专题资料整理候选事件。
2. 规范标题、年代、政权、人物、地点和来源定位。
3. 合并同名异写与重复事件，划定历史过程和子事件边界。
4. 编写基础摘要并分配分类、影响力和布局。
5. 按历史转折意义、跨领域影响和公众认知度选取核心事件。
6. 扩写 200 条核心档案并建立人物与事件关系。
7. 运行自动校验和时期抽样复核。

内部可按时期分批提交，但功能分支在总数、配额和质量门槛全部通过后才进入合并评审。任何中间批次都不得部署到生产站替换完整数据。

## 错误处理

- 缺少目录文件、数量不符、来源不足或引用失效时编译失败且不改动现有生成目录。
- 单条事件错误必须报告文件、事件 ID、字段路径和原因。
- 核心 Markdown 找不到目录事件，或目录标为 `core` 却没有 Markdown 时编译失败。
- 基础档案不因缺少核心详情而报运行时错误；前端按 `detailLevel` 渲染。
- 时代分包加载失败时继续显示紧凑摘要并提供局部重试，不影响其他事件浏览。
- 搜索 Worker 或 WebGL 失败时继续使用现有前缀搜索和二维时间轴降级。

## 测试与验收

### 内容与 Schema

- 精确验证 1200 条事件和 200 条核心事件。
- 精确验证九时期配额和核心配额。
- 覆盖基础记录、核心合并、来源定位、争议年代和全部失败路径。
- 验证现有 30 条核心事件迁移前后关键字段和人物关联不变。
- 验证规范化重复、疑似重复、父子关系和跨记录引用。

### 功能

- 使用真实生产索引验证事件列表包含 1200 条，而非调用测试 fixture 生成器。
- 从每个时期抽取基础和核心事件，验证搜索、筛选、侧栏和完整档案。
- 验证人物、地点、来源、前后事件和浏览器返回。
- 验证基础档案不会渲染虚假的核心章节。
- 验证 3D 和 2D 降级模式都能访问全部事件。

### 性能

- 保留现有 1200 条确定性模拟数据作为算法压力测试。
- 另用真实 1200 条索引运行浏览器集成测试。
- 检查首屏索引体积、搜索初始化时间、聚类响应、时代切换和移动端内存。
- 桌面和移动端均检查外层聚类、逐层放大、事件选择与档案返回。

### 完成标准

- `npm run history:check` 报告 1200 条事件、200 条核心事件和 0 个错误。
- 九时期事件数和核心数与本设计表格完全一致。
- 所有事件至少一个具体来源引用，核心事件至少两个不同来源。
- 完整测试套件、TypeScript 和 Vite 生产构建通过。
- Netlify Deploy Preview 可浏览 1200 条事件并打开基础与核心档案。
- PR 合并后再由 Netlify 自动发布生产站，不跳过预览验证。
